# Design

This document explains the choices behind Veilproof: the group, the commitments, each Sigma protocol and its transcript, the Fiat-Shamir transform, the OR-proof simulation, and how the range proof composes bits.

## The group, and why RFC 5114

Every proof in this crate operates in a single fixed group: the multiplicative group of integers modulo `p`, restricted to the unique subgroup of prime order `q`, generated by `g`. Concretely, `p` is a 2048-bit prime, `q` is a 256-bit prime dividing `p - 1`, and `g` is an element with `g^q mod p == 1` and `g != 1`.

These parameters come directly from RFC 5114 section 2.3, the "2048-bit MODP Group with 256-bit Prime Order Subgroup" (commonly called group id 24). They are hardcoded as big-endian hex constants in `src/group.rs`, not generated or invented by this project. Using a published, independently reviewed group instead of rolling new parameters removes an entire category of mistakes, a badly chosen prime or a generator that does not actually have prime order would quietly break every soundness guarantee below.

On startup, and in a test, the crate runs a self-check: it recomputes `g^q mod p` and confirms the result is exactly 1, and confirms `g` is not 1. That is a direct, executable proof that `g` really does generate the order-`q` subgroup this whole system depends on, not just an assertion in a comment.

Working in a prime-order subgroup, rather than the full group modulo `p`, matters for a subtle reason: it means every nontrivial element has a well-defined discrete log modulo `q`, and every element's inverse can be computed as `x^(q-1) mod p` (Fermat's little theorem applied inside the subgroup), which this crate uses instead of an extended Euclidean algorithm.

Every group element handed to a verifier, from anywhere, statement or proof, is checked against `[1, p)` and against the subgroup membership test `x^q mod p == 1` before it is used in any equation. An element that fails either check is rejected with a typed error. This closes off small-subgroup and out-of-range attacks where a dishonest prover hands the verifier a value chosen outside the intended group to smuggle extra freedom into an equation.

## Pedersen commitments, and the h caveat

A Pedersen commitment to a value `m` with blinding `r` is `C = g^m * h^r mod p`, where `h` is a second generator of the same subgroup. Two properties matter: `C` reveals nothing about `m` on its own (it is uniformly distributed over the subgroup for a random `r`, this is the hiding property), and nobody can open the same `C` to two different values (this is the binding property, and it holds as long as nobody knows the discrete log of `h` with respect to `g`).

That last clause is the caveat that has to be stated honestly. If whoever chose `h` also knew `x` such that `h = g^x`, they could compute a false opening of any commitment they wanted: given `C = g^m h^r`, pick any `m'`, solve `r' = r + (m - m') * x mod q`, and `C = g^m' h^r'` also holds. Binding is only as strong as the guarantee that nobody knows that `x`.

Veilproof derives `h` as `h = g^s mod p`, where `s = SHA256("veilproof/pedersen-h/v1") mod q`, using this crate's own SHA-256 implementation and a fixed, published domain-separation string. This is the standard "nothing up my sleeve" pattern: because `s` is pinned to the output of a hash function on a string chosen before any commitment existed, nobody, including the author of this project, can claim to know a discrete log relating `g` and `h`, since finding one would mean inverting SHA-256.

This is still a teaching-grade convenience, not a substitute for a real trusted setup or a verifiable process run by multiple parties. A deployment that actually depends on nobody knowing `log_g(h)` should use a process it can point to and defend under adversarial scrutiny, this hash-to-exponent trick is a legible stand-in for that, appropriate for a project meant to be read, not a production guarantee.

## The Fiat-Shamir transform

Every Sigma protocol below is naturally a three-move interactive protocol: the prover sends a commitment `t`, the verifier sends a random challenge `c`, and the prover replies with `z`. Fiat-Shamir removes the verifier from the loop entirely by replacing the random challenge with a hash of everything public so far: `c = H(statement, t) mod q`.

Veilproof implements this with a `Transcript` type (`src/transcript.rs`) that appends every public value in a fixed, labeled, length-prefixed order, then hashes the whole buffer with SHA-256 and reduces the result modulo `q`. Length-prefixing every field, rather than concatenating raw bytes, is what stops two different sequences of fields from ever hashing to the same transcript by having a field boundary shift, a canonicalization bug that has broken real protocols before.

Because the verifier recomputes the same transcript and the same challenge from the same public values, a proof is a fixed, deterministic function of the witness and the prover's random nonce, nothing is sent that a passive verifier could not compute for itself except the exact `z` that only someone who actually knows the witness could produce.

## Schnorr proof of knowledge of a discrete log

Statement: a public `y`. Witness: a secret `x` with `y = g^x mod p`.

Transcript: prover picks random `k`, sends `t = g^k mod p`. Challenge `c = H(g, y, t) mod q`. Response `z = k + c*x mod q`.

Verification equation: `g^z == t * y^c mod p`.

Why it works: expand the right side using `y = g^x` and the honest `t = g^k`, giving `t * y^c = g^k * g^(cx) = g^(k + cx) = g^z`, which is exactly the left side. A prover who does not know `x` would have to guess `k` after already knowing `c` (impossible, `t` is fixed before `c` exists) to make the equation balance, so this same algebra is also why a wrong witness or a tampered `t` or `z` fails to verify, the equality simply stops holding.

## Pedersen commitment opening proof

Statement: a public commitment `C`. Witness: `(m, r)` with `C = g^m * h^r mod p`.

This is the same idea as the Schnorr proof above, generalized to two exponents and two generators. The prover picks random `k_m, k_r`, sends `t = g^k_m * h^k_r mod p`. Challenge `c = H(g, h, C, t) mod q`. Responses `z_m = k_m + c*m mod q`, `z_r = k_r + c*r mod q`.

Verification equation: `g^z_m * h^z_r == t * C^c mod p`.

## The OR-proof simulation

The bit proof needs to show `C` opens to `0` or `1`, without revealing which, and a plain Schnorr-style proof only ever shows one specific statement is true. The standard fix, due to Cramer, Damgard, and Schoenmakers, is to prove a disjunction by genuinely proving the true branch and simulating the false one, then binding both branches together with a single Fiat-Shamir challenge.

Rewrite the two branches as discrete-log statements with base `h`: branch 0 claims `C = h^r` (true exactly when the committed bit is 0), branch 1 claims `C * g^-1 = h^r` (true exactly when the committed bit is 1). A real Schnorr proof of either of these looks identical to the dlog proof above.

The trick that makes an OR-proof possible: a Schnorr transcript can be *simulated* without knowing the witness, if the challenge is chosen first instead of last. Pick `z` and `c` at random, then solve for `t = h^z * target^(-c) mod p`. That `t` makes the verification equation `h^z == t * target^c` hold by construction, even though nobody ever computed a real `k`.

So the honest prover, who knows the bit and its true branch, does this: pick a real random `k` for the true branch and compute its real `t`. For the false branch, pick a random `z` and a random `c`, and simulate `t` as above. Build the transcript from both `t` values (and the commitment), get the single Fiat-Shamir challenge `c`, and set the true branch's challenge to `c0 = c - c1 mod q` (or `c1 = c - c0 mod q` for the other case), which forces the split to be consistent with whichever challenge was already fixed for the simulated branch. Finally compute the true branch's `z` the normal Schnorr way, using its now-determined challenge share.

The verifier checks three things: that `c0 + c1 mod q` equals the real Fiat-Shamir challenge over the transcript, and that both branch equations hold, `h^z0 == t0 * target0^c0` and `h^z1 == t1 * target1^c1`. Nothing in what the verifier checks reveals which branch was simulated, both look like valid, independent Schnorr proofs, only the prover knows which one was real. And because the committed value has to actually be a bit for *either* branch's target to be a genuine power of `h` that the prover can compute a real `t` for, a value that is not 0 or 1 has no branch to anchor the challenge split to, and a forged proof fails the `c0 + c1 == c` check with overwhelming probability.

## The range proof

A range proof that a committed value `m` lies in `[0, 2^n)` is built by decomposing `m` into its bits `b_0, ..., b_{n-1}`, committing to each bit separately as `C_i = g^(b_i) * h^(r_i) mod p`, and proving each `C_i` is honestly a bit commitment with the OR-proof above.

The bit commitments are tied back to a single value commitment through the Pedersen homomorphism. If the overall blinding factor is chosen as `r = sum_i r_i * 2^i mod q`, then:

```
product_i (C_i)^(2^i) = product_i (g^b_i * h^r_i)^(2^i)
                       = g^(sum_i b_i * 2^i) * h^(sum_i r_i * 2^i)
                       = g^m * h^r
                       = C
```

So a verifier who checks every bit's OR-proof, then recomputes `product_i (C_i)^(2^i) mod p` and confirms it equals the claimed commitment `C`, is convinced that `C` opens to some value that is a sum of `n` verified bits, which is exactly the set `[0, 2^n)`, without learning `m` or any individual bit along the way.

This crate caps `n` at 32 bits (`range_proof::MAX_BITS`). Both proof size and verification cost are linear in `n`, since each bit needs its own commitment and OR-proof, so this composition is appropriate for modest ranges, not for the wide 64-bit ranges a production system (typically using a logarithmic-size construction like Bulletproofs) would need.

An honest prover cannot produce a range proof for a value outside `[0, 2^n)` at all, there is no witness: the value cannot be decomposed into `n` bits that sum back to it. `prove()` checks this up front and returns a typed error rather than attempting to build a proof it cannot complete.

## The Chaum-Pedersen equality proof

The equality proof (`chaum_pedersen`) proves that two public values share one secret exponent: that there is a single `x` with `y1 = g^x mod p` and `y2 = h^x mod p`, on two different bases `g` and `h`. This is the workhorse behind verifiable re-encryption and shuffle proofs, where you need to show a transformation reused the same secret.

The prover picks one random `k`, sends `t1 = g^k` and `t2 = h^k`, derives `c = H(g, h, y1, y2, t1, t2) mod q`, and replies with a single `z = k + c*x mod q`. The verifier checks both `g^z == t1 * y1^c` and `h^z == t2 * y2^c`. Because there is only one response `z` and it has to satisfy both equations at once, the only way to pass is for `y1` and `y2` to genuinely share the exponent `x`. A prover who used different exponents for the two bases, or computed `z` from the wrong `x`, fails at least one equation. As with Schnorr, `x` never appears in the transcript.

## The 1-of-n ring proof

The ring proof (`ring`) generalizes the two-branch OR of the bit proof to `n` branches over public keys. Given a public ring `y_0, ..., y_{n-1}` with each `y_i = g^{x_i}`, the prover shows it knows the discrete log of one of them without revealing which. It runs the real Schnorr protocol for the single index `j` it holds a secret for, and simulates every other index by choosing that branch's response `z_i` and challenge share `c_i` first, then solving `t_i = g^{z_i} * y_i^{-c_i}` so the branch equation holds by construction.

A single Fiat-Shamir challenge `c = H(g, y*, t*) mod q` binds the whole ring. The simulated shares are fixed before `c` is known, and the real branch absorbs the remainder, `c_j = c - sum_{i != j} c_i mod q`, which only the holder of `x_j` can turn into a valid response. The verifier checks that all shares sum to `c mod q` and that every branch equation holds. A forger who knows no secret can satisfy the individual equations by simulating every branch, but cannot make the freely chosen shares sum to a challenge that itself depends on the resulting `t` values, so the sum check fails with overwhelming probability. The proof has the same shape for every index, which is what hides the prover's position, and the ring size is capped at `ring::MAX_RING` so a hostile serialized proof cannot force an unbounded allocation.
